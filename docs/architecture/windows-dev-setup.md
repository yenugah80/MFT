# Developing MFT on Windows

Development moved from a Mac to a Windows machine as of 2026-09-16. This
doc covers what changes, what doesn't, and how to get a fresh Windows
machine running.

## What fundamentally changes: iOS needs a Mac for anything local

Xcode, the iOS Simulator, and raw `xcodebuild` archives are Mac-only —
there is no Windows equivalent, full stop. That rules out:
- Running the app in a local iOS Simulator to verify a fix before it
  reaches a real device.
- The old raw-Xcode-archive path previously used as an EAS-quota fallback
  (see `mft-app-store-launch-status` memory) — moot anyway, since
  2026-09-16 the project standardized on `eas build` for iOS specifically
  *because* a raw archive silently shipped without the OTA update config
  baked in (missing `EXUpdatesRequestHeaders` in `Expo.plist`) while `eas
  build` — which runs its own fresh `expo prebuild` on Expo's cloud
  infrastructure — does not have that failure mode.

**What still works identically from Windows:** `eas build --platform ios`
compiles remotely on Expo's macOS cloud infrastructure. iOS credentials
(Distribution Certificate + Provisioning Profile) are already managed
remotely by EAS, not stored in any local Keychain — confirmed via a build
log on 2026-09-15/16 ("Using remote iOS credentials (Expo server)") — so
there's nothing device-specific to re-provision. iOS testing going forward
means: OTA-publish or build, then verify on a real device via TestFlight —
which is how most verification actually happened even when a Mac was
available, since a Simulator run only proves the JS logic works, not real
push-notification delivery, real network conditions, or actual TestFlight
update-check behavior.

**What stays fully local on Windows:** Android. Android Studio + emulator
run natively; `expo run:android` works the same as it did on the Mac.
Backend (Node/Express) development is unaffected either way.

## Recommended setup: WSL2, not native Windows

Use WSL2 (Windows Subsystem for Linux) for the actual dev shell — Metro,
Watchman, and the various native-module builds in `node_modules` have a
long history of path- and permission-related breakage on native Windows
that WSL2's Linux filesystem sidesteps. Do all `npm install`/`npm run
dev`/git work from inside WSL2, not PowerShell/cmd.

Android Studio and its emulator are the one exception — install those on
Windows proper (not inside WSL2), since the emulator needs direct access
to Windows' virtualization (Hyper-V/WHPX). `expo run:android` from WSL2
can still target a Windows-hosted emulator; verify this works before
relying on it, since the exact WSL2↔Windows ADB bridging setup can be
finicky depending on WSL2 version.

## First-time setup checklist

1. Install WSL2 (`wsl --install` from an admin PowerShell), then a Linux
   distro (Ubuntu is the safe default).
2. Inside WSL2: install Node.js (match the version this project was last
   verified against — check `backend/package.json`/`mobile/package.json`
   `engines` field if present, otherwise use current LTS), git, and the
   Railway CLI (`npm install -g @railway/cli` or the install script).
3. Clone the repo: `git clone <repo-url> MFT && cd MFT`
4. `npm install` in both `backend/` and `mobile/` (this repo is not a
   single-root npm workspace for install purposes — check each directory).
5. **Restore the 7 gitignored secret files** from the pre-return backup —
   see `~/Desktop/MFT-SECRETS-BACKUP-BEFORE-RETURNING-MAC/README.md` from
   the old Mac (copy that whole folder over first). Each file's exact
   destination path is listed there: `backend/.env`,
   `backend/firebase-service-account.json`, `mobile/.env`,
   `mobile/AuthKey_XYN85P5666.p8`, `mobile/GoogleService-Info.plist`,
   `mobile/google-services.json`, and the repo-root `.env.local`.
6. Install local Postgres for backend dev (see
   `mft-no-dev-environment` memory for why this exists and how it's used)
   — via WSL2's package manager (`apt install postgresql`) or Docker; this
   does not carry over from the old Mac and needs to be freshly seeded.
7. `npx eas login` (mobile/) and `railway login` (repo root) — both are
   account-based, not machine-based, so existing credentials work once
   logged in again from the new machine.
8. Verify: `cd backend && npm run dev` boots the API; `cd mobile && npm
   start` boots Metro; `npx eas build:list` shows the existing build
   history (confirms EAS account access carried over correctly).

## Things that do NOT carry over automatically

- Xcode DerivedData / local `ios/` build artifacts — irrelevant on Windows
  anyway (`ios/` is gitignored and regenerated by `expo prebuild`, which
  only runs as part of `eas build` now).
- Local Postgres data — needs re-seeding, not just reinstalling.
- Any shell aliases/scripts that lived only in the old Mac's shell profile,
  not the repo.
